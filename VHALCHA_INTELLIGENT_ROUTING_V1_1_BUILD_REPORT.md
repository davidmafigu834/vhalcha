# Vhalcha Intelligent Routing V1.1 — Correctness and Cost Integrity

## 1. Executive summary

This phase repaired the routing foundation. It did not add vendors, billing products, or a semantic classifier.

On the Cost strategy, selection is now a sort: among models that are allowed, capable, healthy enough, inside the context window, and inside the hard budget, Vhalcha chooses the lowest estimated cost. Tie breaks are deterministic. A quality weight can no longer make a $0.27 route beat a $0.0162 route.

The three audited P0s are fixed in code and covered by tests:

- Cost no longer prefers a much more expensive model.
- Fallback budget raises use the same scope and row locks as the original reservation.
- A billable first provider response is kept when a later attempt runs. The request total is the sum.

Vhalcha still does not understand semantic task difficulty. Request size is message length.

This is not a production declaration that Vhalcha reduces customer spend by a measured percent. No real customer traffic was measured.

## 2. P0 fixes

### P0-1 — Cost selected Premium at $0.27 over Economy at $0.0162

`packages/routing/src/select.ts` no longer scores Cost with `1 / (1 + costUsd * 1000)` plus a quality weight. Cost orders survivors by estimated cost. The audit case is a unit test. Economy is selected, and the reason is `Lowest estimated cost among qualifying models.`

### P0-2 — Fallback raise used AI-system spend and did not lock

`reserve`, `raise`, and `headroom` share one calculation: scope-specific finalized usage, unexpired holds, hard-limit checks, and `FOR UPDATE` on the blocking budget rows. Organisation and environment budgets no longer fall through to AI-system spend.

### P0-3 — Premium escalation dropped the first billable response

Each provider execution is written to `request_provider_attempts`. Token-priced cost from every billable attempt is summed onto the request. A later attempt is reserved as already-billed actual cost plus the next estimate. If that raise fails, the next model is not called.

## 3. Cost strategy redesign

For `routing_strategy = cost` the order is:

1. Drop models that are not the runtime provider, not allowed, prohibited, unhealthy, missing a required capability, outside the context window, unpriced, over the request cap, or over remaining hard budget.
2. Sort survivors by lowest estimated cost.
3. Break ties only when the absolute cost difference is at most `1e-8`, then by healthier provider, lower expected latency, stronger tier, then model id.

Cost does not use a quality weight.

## 4. Balanced scoring changes

Balanced, Quality, and Latency still mix cost, tier, health, and latency. The cost term is `cheapest survivor / this candidate`, so a 16x gap stays visible at $0.00001 and at $100. The old `1 / (1 + costUsd * 1000)` term is gone. Regression tests cover those scales for the Cost strategy, which must still pick the cheaper capable model.

## 5. Explanation correctness

`explainSelection` builds sentences from the candidate set. It emits `Lowest estimated cost among qualifying models.` only when the selected estimate is less than or equal to every other survivor within `1e-8`.

Other strategies use the sentences specified for Balanced, Quality, and Latency. Supporting facts include selected cost, next-cheapest cost on Cost, qualifying count, health, required capabilities, and request size. Nothing is generated by a model.

## 6. Budget and reservation changes

`committedForBudget` chooses AI-system, environment, or organisation usage the same way for reserve, raise, and routing headroom. Routing no longer subtracts only AI-system spend and no longer ignores holds.

A candidate that cannot fit in `headroom` is removed before ranking, so the router does not select a model the reservation would reject for a known hard limit. A concurrent race can still fail closed at `reserve`. There is no retry loop.

## 7. Fallback accounting

`raise` locks the request's reservation rows and the blocking budget rows before it reads holds. Projected spend is finalized usage plus active holds, minus this request's current hold, plus the new total.

For escalation that new total is billable actual so far plus the next estimate. The pre-request `estimated_savings` value is not rewritten when fallback changes the model.

Tests:

- Organisation hard limit $100, other-system spend $90, this-system spend $5, hold $1, raise to $6: rejected.
- The same shape for an environment budget: rejected.
- System budget $100 with $5 spend: raise to $6 allowed, raise to $96 rejected.
- Two concurrent raises from $10 to $80 against a $100 system budget: one succeeds and one is rejected.

## 8. Provider-attempt ledger

`request_provider_attempts` stores organisation, request, optional routing decision, attempt number, provider, model, reason, status (`succeeded`, `failed`, `escalated`), token counts, estimated cost, actual token-priced cost, error code, billable flag, and timestamps. It does not store prompts, knowledge text, or credentials.

The acceptance escalation case recorded `standard-model` as escalated and `premium-model` as succeeded. Both were billable. Request usage cost was `0.00010560`, matching the sum of the attempt costs.

## 9. Pricing single source of truth

Runtime rates come from `model_catalogue`. `calculateTokenCost` only does arithmetic. The old `modelPrices` registry in `packages/providers` is gone. Routing, reservation, usage, baseline estimates, and savings all price through that function with a catalogue rate.

Tests may pass fixture rates. Production code does not keep a second rate table.

## 10. Price freshness

Catalogue columns: `currency`, `price_effective_at`, `price_verified_at`, `price_source`.

`VHALCHA_MAX_PRICING_AGE_DAYS` defaults to 90. Ninety days is long enough for a published rate card and short enough that an unverified year-old price is not shown as an optimisation benefit. Routing may still use a stale rate. Savings are suppressed and the explanation says pricing data requires verification.

Migration `0006_routing_integrity.sql` updates existing rows in place and sets `price_verified_at` to the migration time. It does not rely on `ON CONFLICT DO NOTHING` for price changes. Later updates are `pnpm db:sync-prices`, which runs `packages/database/src/catalogue-prices.ts` and updates matching rows. There is no vendor scrape.

The rates stamped in this phase are the rates already in the catalogue, with verification text dated 2026-09-29. They were not re-fetched from OpenAI during this phase.

## 11. Baseline validation

A baseline must exist in the catalogue, have finite prices, and be organisation-approved. The routing form label is `Baseline model (must be organisation-approved)` and the dropdown lists approved models only. A blocked model is not stored as a hypothetical comparison baseline.

## 12. Request-size terminology

The classifier sets `request_size` to `small`, `medium`, or `large` from message length. Thresholds remain 400 and 2000 estimated input tokens. The same value is still written to `routing_decisions.complexity` because renaming that column was not worth the migration risk. The dashboard says Request size and maps historical `low` to small and `high` to large.

The sentence `Analyse this acquisition agreement and identify financial, legal and operational risks.` classifies as request size small and capability `chat`. Routing does not treat that sentence as semantically difficult.

Length no longer adds `reasoning` or `long_context`. The context window remains the filter for long input.

## 13. Capability limitations

The public chat schema is text. `usesTools` and `requiresVision` stay false. The product does not claim vision or tool routing.

Structured output is still the word `json`. That is a weak compatibility signal, documented in the classifier. It is not a schema validator.

## 14. Unified token estimator

`estimateRequestTokens` is the estimate used by routing, context checks, and reservation. Input tokens are `ceil(characters / 4)`. Output tokens are the client `max_tokens` or 256 / 800 / 2000 by request size, then capped by the model max output. Context and price both use input plus that capped output. The reservation default of 4096 is gone.

Estimated and actual usage stay separate. Actual tokens come from the provider response.

## 15. Knowledge regression

Knowledge still runs before routing. The acceptance user message is now `Summarise the approved note.` The retrieved document repeats that sentence so it is retrievable and, together with the other retrieved chunks, exceeds the economy context window of 1000 tokens. Economy is not selected. Standard is selected. The short classify request in the same run still selects economy, so the upgrade is from the retrieved context.

## 16. Dashboard changes

The gateway overview keeps its layout. Labels now distinguish estimated route cost, estimated baseline cost, estimated optimisation benefit, and actual token-priced cost. The overview states that the benefit is model token pricing and is not the provider invoice. A negative aggregate is labelled `Estimated additional cost` and formatted as a negative currency amount.

Request detail shows qualifying count, rejection codes, selection reason, estimated route cost, next-cheapest cost, pricing verified timestamp, fallback, knowledge yes/no, per-attempt token-priced cost, and the request total. It does not show prompts, knowledge text, or keys.

These pages were typechecked by `next build`. They were not clicked through in a browser in this session.

## 17. BYOK corrections

A partial unique index allows one active connection per organisation, environment, and provider. Connecting a new key disables the previous active row for that triple. New organisation connections are `Unverified`. There is no vendor ping in this phase, so the UI does not call them healthy.

If `VHALCHA_SECRETS_KEY` cannot encrypt, the connect form is hidden and the server action rejects the attempt. The gateway still boots so the platform OpenAI credential can be used. This is option B from the task, not a boot failure of the whole gateway.

## 18. Provider timeout

Non-streaming and stream-open HTTP calls use `AbortSignal.timeout`. `VHALCHA_PROVIDER_TIMEOUT_MS` defaults to 60000. Timeout and abort map to `provider_unavailable` without the vendor body. A unit test aborts a hung non-streaming fetch.

## 19. Provider health

A stream is not marked successful when it opens. Success is recorded after the stream finishes. A mid-stream failure or client disconnect is a failure. Health read-modify-write locks the existing health row with `FOR UPDATE`. Two inserts of a brand-new health row can still race; that case is not newly serialized beyond the existing unique key.

## 20. Idempotency

States are `in_progress`, `completed`, `retryable_failed`, and `terminal_failed`. The same fingerprint may retry a `retryable_failed` key. `in_progress`, `completed`, and `terminal_failed` do not start another provider call. Budget and other policy failures are terminal. A provider failure with no billable usage is retryable. Any billable attempt makes the key terminal. The body is not replayed from Redis. The fingerprint is still required.

## 21. Database and RLS

Migration `0006_routing_integrity.sql` adds pricing provenance, provider verification status, the one-active connection index, and `request_provider_attempts`.

The attempts table is granted to `vhalcha_app` and `vhalcha_worker`, with row level security forced and `app.tenant_visible(organisation_id)`. A test as `vhalcha_app` sees no attempts without tenant context, sees its own attempt inside the tenant, and sees none for the other organisation.

`model_catalogue` stays global and is not tenant-scoped. The application role can select it and cannot update it. That is why the acceptance harness does not age live prices itself.

## 25. Remaining P0

No audited P0 from Intelligent Routing V1 remains open in the paths this phase changed. Cost ordering, scoped locked raises, and billable attempt totals are implemented and tested.

This is not a claim that the product has no operational risk. See production readiness.

## 26. Remaining P1

- The HTTP path that suppresses savings for a stale catalogue row is implemented and not driven by the live acceptance database, because the app role cannot update prices.
- Organisation provider connections stay Unverified. There is no safe vendor ping yet.
- Price updates are manual via `pnpm db:sync-prices`. Verification was stamped from the existing rate card at migration time.
- `routing_decisions.complexity` and `requests.estimated_cost_usd` keep historical names. The UI describes request size and actual token-priced cost.
- The `json` keyword is still the structured-output signal.
- Vision and tools cannot be requested by the public schema.
- Provider health insert for a first-seen model is not fully serialized beyond the unique key.
- Idempotency retry depends on Redis plus the absence of billable usage. It is not a cross-store transaction.
- Dashboard label changes were not exercised in a browser.

## 27. Production readiness

Not ready to claim measured customer savings or semantic routing.

Ready, for the tested scope: Cost selection among qualifying catalogue models, hard-budget enforcement on fallback for organisation, environment, and AI-system scopes, a tenant-scoped attempt ledger, one catalogue price formula, and savings labelled as estimates.

Not ready: real workload measurement, a vendor price review, verified BYOK checks, and any statement that a long or important sentence is understood as a hard task.

## 28. Recommended next phase

Measure real routed traffic before publishing a savings percentage. Keep Cost boring. Put quality and cost tradeoffs in Balanced only.

Next product work that would change a claim:

- A request schema for tools or images, if those routes are going to be advertised.
- A scheduled price review that updates `price_verified_at` only after a human confirms the rate.
- An optional provider credential check that stores verified or failed and never stores the vendor body.

Do not add another model to the request path to fake semantic complexity.
